# What You Check, Not What You Asked For

Proof of concept for the article *What You Check, Not What You Asked For*
([English](https://blog.ragnagrok.com/en/2026-11-02-lo-que-chequeas-no-lo-que-pediste) ·
[español](https://blog.ragnagrok.com/es/2026-11-02-lo-que-chequeas-no-lo-que-pediste)):
a toy, with no agents involved, that shows the article's central distinction. A check can be
**the definition** of correct, or **a sample** of it. An implementation that only knows the
sample passes the sample 100% and does nothing else.

The idea in one line: a lookup table of answers passes a fixed suite; it doesn't pass a
specification checked on new cases every run.

```
implementation  examples   saved    fresh
insertionSort   12/12      50/50    OK (1000 new cases)
fromExamples    12/12      21/50    FAILED on [0,-1]
fromSaved       4/12       50/50    FAILED on [0,-1]
```

## What's here

The task is the smallest one with an unambiguous definition: sort a list of numbers.

| File | What it is |
|---|---|
| `src/Spec.hs` | The definition: the output is in order and has exactly the input's elements. It lists no cases. |
| `src/Examples.hs` | A fixed suite of 12 example tests, input and expected output. The article's "222 tests", in miniature. |
| `src/Saved.hs` | 50 random cases, drawn once from seed 42 and saved. Generated by `tools/Freeze.hs`. |
| `src/Implementations.hs` | Three implementations. `insertionSort` sorts. `fromExamples` looks the answer up in the example suite and returns anything else unchanged. `fromSaved` does the same with a table of answers for the saved cases (`src/SavedAnswers.hs`). |
| `app/Main.hs` | Runs the three implementations against three checks and prints the table above. |
| `check.sh` | Verifies the table: who passes what, and who fails. |

The three checks:

- **examples**: the fixed suite. A sample, written by hand.
- **saved**: the definition, but only on the 50 saved cases. Also a sample: generated at random
  once, and fixed from then on.
- **fresh**: the definition, on a thousand new random cases each run, with QuickCheck.

## What it shows

- **A sample can be passed without doing the job.** `fromExamples` scores 12/12 on the example
  suite. It's a lookup table: the "dead or absent library" of the article, in two lines.
- **Random cases that never change are still a sample.** `fromSaved` scores 50/50 on the saved
  cases, even though they were generated at random. That's why the article asks that seeds
  change, and treats saved failures as regression tests, not as a verdict.
- **A definition checked on new cases can't be passed that way.** Both tables fail the first
  time they meet an unsorted list they haven't seen, and QuickCheck shrinks the failure to two numbers.
  Only `insertionSort` passes all three checks.

## Running it

With GHC 9.12 and cabal:

```sh
./check.sh          # runs the checks and verifies the table
cabal run checks    # just the table
cabal run freeze    # regenerates src/Saved.hs and src/SavedAnswers.hs from seed 42
```

## What this proof of concept doesn't cover

- **It doesn't reproduce the paper.** No agents, no Angular, no Playwright. It illustrates the
  distinction the article draws, with the smallest possible example. The paper's code and data
  are at [github.com/yanuoma/b2t](https://github.com/yanuoma/b2t).
- **The cheating is written by hand.** In the paper, nobody wrote a lookup table on purpose:
  the agents put the behavior where the tests looked. Here the two tables are deliberately the
  laziest possible implementations, to make the gap visible.
- **It only shows one of the two distances.** The article says a check can fall short in how
  complete it is and in where it looks (the paper's tests could only observe the demo, not the
  library). This toy only covers completeness.
- **A definition isn't always available.** Sorting has a two-line specification. Many real
  features don't, and then the article's advice is about who gives the final verdict, not about
  writing a perfect spec.
